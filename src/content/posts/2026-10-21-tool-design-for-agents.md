给普通系统写接口，读者是人：文档可以长，参数可以多，报错可以甩一个堆栈。

给 Agent 写工具不一样。你的读者是一个只会看描述、不会看源码、还特别擅长"自信地猜"的模型。接口设计的每一个细节，都会直接变成它的行为。

## 工具描述就是提示词

模型决定调不调用一个工具，主要依据三件事：工具名、描述、参数结构。

所以描述里最好明确写：

- 这个工具**做什么**。
- **什么时候该用**它。
- **什么时候不该用**它。
- 会返回什么，失败时是什么样。

一句"查询订单"信息量太低。更好的写法是"按用户邮箱查询订单列表，只读。当用户询问订单状态、物流进度时使用；不要用于修改订单"。

## 单一职责

一个工具干一件事。把"查订单、改地址、申请退款"塞进同一个工具，模型很容易选错参数，出错后也难以定位。

工具数量也不是越多越好。工具太多会让模型在选择上消耗注意力，描述之间还容易互相冲突。

## 参数要严格

能用枚举就别用自由文本，能加范围就别留空。

```json
{
  "name": "refund_order",
  "description": "对已支付的订单发起退款。仅在用户明确确认退款金额后调用。",
  "inputSchema": {
    "type": "object",
    "properties": {
      "order_id": { "type": "string", "pattern": "^ord_[0-9]{8}$" },
      "reason": {
        "type": "string",
        "enum": ["七天无理由", "商品损坏", "重复支付", "其他"]
      },
      "amount": { "type": "number", "minimum": 0.01 }
    },
    "required": ["order_id", "reason", "amount"]
  }
}
```

约束越明确，模型瞎编的空间越小，服务端也越好做校验。

## 返回值要短

工具返回的内容会进入上下文，成为下一轮的输入。返回一整页 JSON，模型可能抓不住重点，还白白消耗窗口。

好的返回结构通常包含三部分：

- 状态：成功还是失败。
- 关键结果：模型真正需要的字段。
- 下一步提示：比如"结果超过 20 条，请缩小时间范围"。

## 错误信息写给人看，也写给模型看

模型看到 `Error: 500` 什么也做不了。看到"订单号格式不对，应为 ord_ 开头加 8 位数字"才有机会自己修正。

错误信息应该可行动：说清哪里错了、期望是什么、可以怎么重试。

## 幂等与超时

Agent 会重试。网络抖动、模型判断失误、用户重复点击，都可能导致同一个工具被调用两次。

写操作要支持幂等键，避免重复退款、重复发消息。所有工具都要有超时，别让一个卡住的调用拖死整轮对话。

## 权限与确认

工具是模型的手脚，权限就是它能造成破坏的上限。

- **最小权限**：只读工具不要给写权限。
- **危险操作二次确认**：删除、支付、发邮件、执行命令，必须由用户明确确认。
- **隔离执行**：代码执行类工具放进沙箱，限制网络和文件系统。

不要指望在提示词里写一句"不要执行危险操作"就安全了。模型可能被外部内容诱导，也可能只是理解错了。

## 怎么测工具

两层测试：

1. **直接调用测试**：绕过模型，验证参数校验、错误处理、幂等性。
2. **模型调用测试**：给模型几个典型任务，看它是否选对工具、填对参数、失败后能否恢复。

第二层最容易被跳过，但它恰恰能暴露描述写得含糊的问题。

## 小结

给 Agent 造工具，本质上是在设计一套"给模型用的界面"。它需要比给人类用的 API 更明确、更收敛、更防御。

工具的边界画清楚了，Agent 的能力才可靠。
