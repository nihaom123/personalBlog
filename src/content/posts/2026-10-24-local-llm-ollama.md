云端 API 又强又方便，为什么还要在本地跑模型？

我用本地模型主要是三个场景：处理不方便上传的数据、在没有网络的路上写点东西、以及反复调试时不想按 token 计费。

## 什么时候该考虑本地

- **数据不能出内网**：合同、病历、内部文档。
- **需要离线可用**：现场演示、出差、网络不稳定。
- **调用量很大但任务简单**：分类、抽取、改写，本地小模型足够。
- **想学习和实验**：改提示词、试工具调用，不用担心账单。

反过来说，复杂推理、长上下文、高质量代码生成，本地小模型目前仍然很难和云端旗舰模型比。

## Ollama 三条命令

Ollama 把模型下载、量化、启动服务都封装好了，适合入门：

```bash
# 安装后拉取并运行一个模型
ollama run qwen3

# 查看本地已有模型
ollama list

# 以 API 方式调用（默认 11434 端口）
curl http://localhost:11434/api/generate -d '{
  "model": "qwen3",
  "prompt": "用一句话解释什么是向量检索",
  "stream": false
}'
```

它的接口和 OpenAI 风格不完全一样，但社区有兼容层，接入现有代码不算麻烦。

## 显存决定你能跑多大

这是最实际的一张表，按量化后的模型大小估算（Q4 级别）：

| 显存 / 统一内存 | 比较舒服的模型规模 |
| --- | --- |
| 8 GB | 3B 到 7B |
| 16 GB | 7B 到 14B |
| 24 GB | 14B 到 32B（量化） |
| 48 GB 以上 | 70B 级别（量化） |

模型放不进显存时会退到内存，速度会明显下降。买硬件之前先想清楚你要跑的规模，别只看参数。

Mac 的统一内存在这件事上有优势，因为显存和内存是同一块。Windows 机器则要关注显卡显存，而不是系统内存总量。

## 模型怎么选

- **中文任务、日常问答**：Qwen 系列是比较稳的选择，工具调用能力也不错。
- **通用英文任务**：Llama 系列生态成熟，资料多。
- **轻量设备**：Gemma 的小参数版本，跑得动、响应快。
- **代码任务**：选专门的代码模型，别用通用模型硬扛。
- **多步 Agent**：优先选工具调用稳定的型号，参数大不等于会调工具。

一个实用建议：先用小模型把流程跑通，确认瓶颈在模型能力上，再换大的。很多时候瓶颈其实在提示词和上下文组织。

## 本地和云端的取舍

| 维度 | 本地 | 云端 |
| --- | --- | --- |
| 隐私 | 数据不出机器 | 取决于服务商策略 |
| 成本 | 一次性硬件投入 | 按量计费 |
| 能力上限 | 受显存限制 | 前沿模型 |
| 延迟 | 稳定、可预期 | 受网络影响 |
| 运维 | 自己负责 | 服务商负责 |

## 团队使用要考虑服务化

个人用 Ollama 够了，团队共用就要考虑并发和调度。常见做法是用 vLLM 这类推理服务，支持批处理和多并发，再配一个网关做鉴权和限流。

别把 Ollama 直接暴露到公网。它默认没有复杂鉴权，适合本机或内网。

## 一个清醒的预期

本地模型能帮你省钱、保隐私、做实验，但它不是云端旗舰模型的免费替代品。

把它用在合适的任务上：分类、抽取、改写、离线辅助。复杂任务该上云就上云，这不是立场问题，是成本问题。
