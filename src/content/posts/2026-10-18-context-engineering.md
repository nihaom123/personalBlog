前两年大家热衷“提示词工程”：加一句“你是一位资深工程师”，换一种输出格式，效果好像真的变好了。

到了 2026 年，这套方法遇到了天花板。原因很简单：当模型足够聪明时，措辞的影响在变小，而**它看到的信息**影响在变大。

## 一个对比

假设你让模型修一个 bug。

提示词工程的做法是：把问题描述写得尽可能详细，加上“请逐步思考”。

上下文工程的做法是：先把相关文件、最近的报错日志、相关提交记录找出来，按重要性排好，再决定哪些放进窗口、哪些不放。

后者的效果通常好得多，因为它解决的是"模型有没有拿到足够信息"，而不是"问题问得漂不漂亮"。

## 定义

Anthropic 的应用团队给过一个很精炼的定义：上下文工程是在有限的注意力预算下，找到**最小的高信号 token 集合**，来最大化期望行为。

关键词有两个：**最小**和**高信号**。不是塞得越多越好。上下文越长，模型越容易忽略中间部分，也越容易被无关信息带偏。

## 四个有效机制

围绕这个定义，生产环境里反复被验证的做法主要有四类：

### 1. 选择

不是把所有文档都灌进去，而是先检索、排序、截断，只留下真正相关的内容。RAG 属于这一类，但选择不只发生在检索阶段，也包括"这个任务需不需要历史对话"。

### 2. 压缩

长会话接近窗口上限时，主动把前面的内容总结成摘要，再用摘要开启新一段。模型会丢失逐字记忆，但能保住语义连续性。

```python
def compact(messages, llm, keep_last=6):
    old = messages[:-keep_last]
    recent = messages[-keep_last:]
    summary = llm.summarize(
        old,
        instruction="保留已做的决定、关键事实、未解决的问题，删除寒暄。"
    )
    return [{"role": "system", "content": f"之前对话摘要：{summary}"}] + recent
```

触发时机很关键。等到超限再压缩，往往已经丢了一次重要信息。

### 3. 记忆

把跨会话有用的东西写出来：用户偏好、项目约定、上次做到哪一步。记忆不是"把聊天记录存下来"，而是有选择地沉淀结构化事实。

### 4. 隔离

把子任务交给独立的子 Agent，只把结论带回主会话，而不是把所有中间过程都塞回主上下文。这是多 Agent 架构真正有价值的地方之一：它首先是一种上下文管理手段，其次才是"分工"。

## 上下文漂移

长任务里常见的一种失败：模型做到第十步时，忘了第一步定下的约束。

解决办法不是反复强调，而是把关键约束固定在系统提示里，并且每一步只保留当前阶段需要的信息。上下文也需要"垃圾回收"。

## 实操清单

- 写清楚这次任务**必须**看到的信息，列出来。
- 给每类信息设预算，比如检索内容不超过窗口的 40%。
- 长会话设置压缩阈值，别等爆窗口。
- 关键约束放在开头和结尾，中间部分模型最容易忽略。
- 每次失败后问一句：是模型不行，还是它没看到该看的东西？

## 常见误区

**误区一：上下文越长越好。** 长上下文会带来更高的成本和更低的信号密度，模型的表现不一定更好。

**误区二：系统提示写得越长越安全。** 规则越多，冲突越多，模型越难判断哪条优先。规则应该少而硬。

**误区三：上下文工程就是 RAG。** RAG 只是"选择"这一环。压缩、记忆、隔离同样重要。
