如果你在 2024 年做过 AI 应用，大概率写过这种代码：给 ChatGPT 写一套插件，给自家 App 再写一套，换一个客户端又要重写一遍。每个模型厂商的 function calling 格式还都不太一样。

MCP（Model Context Protocol）要解决的就是这个 N×M 的重复劳动：把"模型连接外部工具"这件事标准化，让服务端写一次，所有支持协议的客户端都能用。

## 三个角色

MCP 的架构不复杂，记住三个角色就够了：

- **Host**：宿主应用，比如 IDE、桌面客户端、你自己的 AI 产品。
- **Client**：宿主内部负责和 Server 通信的连接器，通常由 SDK 实现。
- **Server**：对外提供能力的一方，可以是本地进程，也可以是远程服务。

一个 Host 可以同时连多个 Server。比如一个 IDE 同时连文件系统、数据库、Git 三个 Server。

## 三种能力

Server 对外暴露的东西分三类：

- **Tools**：模型可以调用的动作，比如查数据库、发消息。
- **Resources**：可以读取的数据，比如文件、文档、日志。
- **Prompts**：预设的提示词模板，通常由用户主动选择。

大多数开发者最先接触的是 Tools，也是权限风险最大的一类。

## 传输方式

本地场景常用 stdio，Server 作为子进程启动，简单、无需网络。远程场景用 HTTP 传输，需要处理鉴权、多租户和网络中断。

2026 年 7 月的新版规范一个明显方向是**无状态化**：减少对长连接的依赖，让 Server 更容易水平扩展。对于需要人确认或补充输入的工具调用，规范提供了多次往返的机制，而不是要求服务端反向发起连接。同时，远程 Server 的鉴权更明确地落到 OAuth 2.1 这一套上。

这些变化的共同目标是：让 MCP Server 更像一个普通的 Web 服务，而不是一个必须一直挂着的特殊进程。

## 安全功课

MCP 把工具接入变简单了，也把攻击面变大了。上线前至少做这几件事：

1. **参数校验**：每个工具参数都用 Zod、Pydantic 或 JSON Schema 校验，绝不把模型生成的字符串直接拼进 shell 或 SQL。
2. **最小权限**：一个 Server 只拿它真正需要的权限。查报表的服务不该有写库权限。
3. **危险操作人工确认**：删除、转账、发邮件、执行命令，必须有显式确认，不能由模型自己决定。
4. **限流与审计**：Agent 会在短时间内密集调工具，按用户、按工具记录调用日志，才能事后追责。
5. **隔离**：远程 Server 放在受控网络里，本地 Server 用独立进程和受限目录。

## 一个最小的工具定义

下面只是结构示意，重点是"名字、描述、参数、返回"四件事都要写清楚：

```json
{
  "name": "search_orders",
  "description": "按用户邮箱查询订单列表。只读操作。当用户询问订单状态时使用。",
  "inputSchema": {
    "type": "object",
    "properties": {
      "email": { "type": "string", "format": "email" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 20 }
    },
    "required": ["email"]
  }
}
```

工具描述是写给模型看的，不是写给同事看的。它需要说明"什么时候用、什么时候不用、会返回什么"，否则模型只能靠猜。

## 什么时候不需要 MCP

如果你只有一个应用、只接一个模型、只有两三个工具，直接写 function calling 更省事。MCP 的价值在复用和生态，不在单点场景。

判断标准很简单：当你要接第二个客户端，或者工具要被多个产品共用时，再上 MCP 不迟。
