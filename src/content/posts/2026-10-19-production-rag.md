很多人对 RAG 的印象还停留在三步：把文档切块、算向量、搜出来塞给模型。

这套流程做个 Demo 确实够用。但一旦真实用户开始问奇怪的问题、文档开始每天更新、答案开始被要求"必须有出处"，你会发现坑几乎都不在这三步里。

## 一条完整链路

### 1. 解析与清洗

PDF、网页、表格、扫描件，解析质量直接决定后面所有环节的上限。页眉页脚、导航栏、重复水印都要清掉，否则它们会被当成正文检索出来。

这一步做不好，后面换再好的 embedding 模型也救不回来。

### 2. 切分与元数据

固定长度切分简单，但会把一句话从中间截断。更稳的做法是按结构切：标题、段落、表格各自成块。

每块至少要带这些元数据：来源、标题、更新时间、章节路径。它们既用于过滤，也用于最后生成引用。

### 3. 查询改写

用户问"上个月那个退款政策改了吗"，直接拿这句话去检索，效果通常很差。

常见处理包括：补全指代、拆成多个子问题、生成同义表达、抽取时间范围做过滤。这一步往往比换模型更能提升召回。

### 4. 混合检索

纯向量检索擅长语义相似，但对精确关键词、型号、人名不敏感。BM25 正好相反。

生产里常见的是两路召回再融合，常用的融合算法是 RRF（倒数排名融合）：

```python
def rrf(rank_lists, k=60):
    scores = {}
    for ranks in rank_lists:
        for pos, doc_id in enumerate(ranks, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + pos)
    return sorted(scores, key=scores.get, reverse=True)
```

参数不一定要调得很精细，先让两路都跑起来，收益通常比单路明显。

### 5. 重排

召回追求"别漏"，重排追求"把最相关的放前面"。用一个交叉编码器对小候选集重新打分，能显著改善前几条的质量。

重排的代价是延迟。候选集别开太大，常见做法是召回 50 条、重排到 8 条。

### 6. 上下文组装与生成

最后才是拼提示词。这里有两个细节经常被忽略：

- **给每段内容编号和来源**，要求模型引用编号，方便用户核对。
- **允许模型说"资料里没有"**。不给出处就自由发挥，是 RAG 最常见的翻车方式。

## 常见坑

| 现象 | 常见原因 |
| --- | --- |
| 检索总是差一点 | 切分破坏了语义，或缺少查询改写 |
| 关键词搜不到 | 只做了向量检索，没有 BM25 |
| 答案看着对但没出处 | 提示词没有强约束引用 |
| 新文档搜不到 | 索引更新有延迟，或元数据过滤写错 |
| 上线后效果变差 | 没有评估集，无法定位是哪一环退化 |

## 先做评估，再谈优化

RAG 的优化很容易变成玄学：换了 embedding、加了重排、改了提示词，感觉好了一点，但说不清好在哪里。

比较靠谱的做法是先准备 50 到 100 条真实问题，人工标注"应该命中哪些片段、正确答案是什么"，然后分别看检索指标和生成指标。

没有这套东西，你无法判断一次改动是优化还是碰运气。

## 一句话总结

RAG 的难点不在"把向量搜出来"，而在**保证模型拿到的是对的、够用的、可核对的信息**。前者是工程，后者才是产品。
